# 牌面 / 桌面 UI 资产的外部参考与吸收记录

本文件记录我们**向哪些开源项目学过什么、采纳了什么、否决了什么以及为什么**。
目的不是罗列仓库，而是让下一轮优化不必从零调研 —— 每条都写清「可迁移的做法」和
「为什么不照抄」。新增一轮调研时，在末尾追加一节，不要覆盖历史结论。

## 怎么用这份文件

改牌面/桌面前先看这里有没有相关结论；如果发现某条结论已经不成立（上游变了、
我们的约束变了），直接在原文上修订并注明日期，比另起一条更不容易失效。

判别一个参考资产是否值得吸收，看三点：

1. **是否零外部依赖** —— 依赖运行环境（系统字体、外部图片、特定渲染器）的资产，
   换台机器就变样。这是公开资产最容易被忽略的硬指标。
2. **光照是否物理自洽** —— 同一张图里高光/阴影的方向是否服从同一个光源。
   自洽了才像实物，不自洽就会「说不出哪里怪」。
3. **是否有回归基线** —— 没有基线就没法判断改动是变好还是变坏，
   「持续优化」会退化成每轮重新赌一次（见 `web/visual-baseline.mjs`）。

## 采纳的做法

### ① 字形走内嵌矢量路径，不用系统字体（2026-09-19）

**来源**：FluffyStuff / SakaiTaka23 / z2labplus 三家**全部**是纯路径，零字体依赖。

**为什么必须改**：我们 v2 用 `<text font-family="KaiTi,STKaiti,SimSun,STSong,serif">`
渲染「萬 / 一~九」。三个问题：

- 楷体、宋体是 **Windows 专有字体**，Linux / Android / iOS 上会静默回退，
  同一张「八萬」在不同设备上字形和字距都不一样。
- 牌桌页面把 SVG 当图片光栅化成 pixi 纹理（`Image` → `canvas`），
  这条路上字体解析更不可控，缺字直接出方块。
- 把专有字体的派生轮廓公开发布有授权风险。

**怎么做的**：`web/tools/extract-glyphs.py` 用 fontTools 从一个 **SIL OFL 1.1 授权的
中文可变/静态字体**抽出十个字形的轮廓，按 em 归一化取整后写入 `web/glyphs.js`，
运行期 `tiles-ui.js` 做一次仿射拟合，直接画 `<path>`。用 TC 而不是 SC：
麻将牌面是「萬」不是「万」。（字体最终选定为楷体而不是宋体，原因见 ⑤。）

**顺带收益**：视觉基线脚本不再需要 `loadSystemFonts: true` —— 基线从此与本机
字体无关，同一份源码在任何机器上光栅化出同样的像素，回归结果才真正可复现。

### ② 单一光源 + 四壁受光（2026-09-19）

**来源**：FluffyStuff 的 `Front.svg` —— 顶部受光的白色色块是**异形的**，
偏向一侧且边缘渐隐，不是左右对称的等高亮条。

**我们原来的问题**：牌身按「纯顶部光照」画（只有顶部高光 + 底部暗边），
但筒子的靶心高光点在**左上**（`cx - r*0.42, cy - r*0.46`）—— 同一张牌上有两个光源。

**怎么做的**：显式声明光源在**左上方（方位角 45°）**，全牌面服从它。按朗伯余弦
定律补齐四壁，凸起与凹陷方向**相反**：

| | 上壁 | 下壁 | 左壁 | 右壁 |
|---|---|---|---|---|
| 凸起（牌身） | 高光 | 暗边 | 亮线 | 暗线 |
| 凹陷（面板） | 暗（投影） | 亮（受光） | 暗 | 亮 |

强度用**多档渐变**而不是两档线性 —— 两档会在色带边缘留下可见的硬转折。

### ③ 令牌单一源（2026-09-19）

**来源**：z2labplus 的符号化颜色定义 + KDE 把牌桌度量抽成独立描述文件。

**怎么做的**：色板与质感强度收敛到 `web/tokens.js`，构建时展开成 `:root{...}`
注入模板与 `site.css`；绘制代码里一个色值都不硬写。加质感开关（如
`fx.edgeLight`）只改这里一处。

### ④ 源码 → 脚本 → 产物 的目录结构（2026-09-19）

**来源**：SakaiTaka23 的 `source/` + `scripts/` + 多套 `built` 变体。

**怎么做的**：`web/tools/extract-glyphs.py` 是脚本，`web/glyphs.js` 是生成物
（文件头标注「自动生成，请勿手改」）。`build.mjs` 的脚本链把 `glyphs.js` 排在
`tiles-ui.js` 之前，并在构建期检查它是否存在 —— 缺了就报错退出，而不是产出一个
万子全是空白面板的页面。

## 否决的做法

| 参考做法 | 为什么没照抄 |
|---|---|
| FluffyStuff 用 `feGaussianBlur` 做柔化受光/投影 | 牌面还要经 `Image`→`canvas`→pixi 纹理这条路径光栅化；滤镜在这条路上既慢又不可靠（33 张纹理每次重建都要跑一遍滤镜）。改用**多档渐变**逼近同样的柔化，零滤镜依赖，`resvg` 与浏览器表现一致。 |
| 直接用它们的 SVG 文件 | 授权虽宽松（CC0），但（a）是日麻 34 种牌面，我们要的是川麻花色与简牌风；（b）每个文件带 Inkscape 元数据，体积大（`Sou1.svg` 单张 60 KB）；（c）我们要能按令牌调材质。**学做法，不用文件**。 |
| 预生成 rotate / merged 等多种变体 | 我们的牌面是运行期按令牌参数生成的，尺寸随容器走（`width:100%` + viewBox）。预生成变体反而失去了参数化能力，收益只在渲染性能上，而我们的瓶颈在牌数（33 张）不在变换。 |
| SVG 滤镜 `feTurbulence` 做绒布/牌背材质 | 同上，滤镜风险高；桌面绒布在 `pixi-table.js` 里本来就用 canvas 逐像素生成，可控性更好，且能做定向拉丝（`feTurbulence` 给不出方向性纹理）。 |

### ⑤ 字体风格：楷体，不是宋体（2026-09-19，同日第二轮）

**怎么发现的**：字形路径化上线后，用指纹量「数字墨迹」，发现「一 / 二 / 三」比 v2 的楷体系统字体**轻了 7~13%**。原因不在字号，而在字体风格：**宋体（serif）的横画天生细** —— 这是宋体的设计特征，不是缺陷。但麻将牌面要的是毛笔楷书那种**匀重笔画**，一 / 二 / 三 恰恰全是横画，于是短板正好落在这几个最简单的字上。

**怎么验证的**：同一套版式参数、同一套渲染口径，只换字体数据做 A/B：

| 指标（牌河尺寸 33×46） | 宋体 Noto Serif TC Bold | 楷体 LXGW WenKai TC Bold |
|---|---|---|
| 「一」墨迹 | 18 px | **29 px（+61%）** |
| 「二」墨迹 | 24 px | **38 px（+58%）** |
| 「三」墨迹 | 26 px | **48 px（+85%）** |
| 数字墨迹总量 | 439 | 449 |
| 一~九 墨迹分布 | 18 ~ 86（极不均） | 29 ~ 67（匀） |

**结论**：换楷体。总和几乎不变，但**重量分布从极不均变成匀重**，且吃紧的 一/二/三 明显变好。代价是万子 detail 指纹 -1.5%~-6%（楷体笔锋曲线更圆润，相邻像素亮度差略低）—— `detail` 只是「边缘能量」的代理指标，笔画匀重比它更重要，这个取舍是明确的。字形数据也从 3.4 KB 涨到 9.1 KB（楷体的笔锋曲线更复杂）。

**代价与边界**：字体从 Noto Serif TC 换成 LXGW WenKai TC（霞鹜文楷，同样是 OFL 1.1）。换字体后抽取脚本报出命令集从 `CHLMVZ` 变成 `HLMQVZ` —— 实测证明「命令集必须构建期校验」这条不是多余的：另一个字体真的会带来不同的命令组合。

**可迁移的判断**：给牌面选字体，第一个要看的不是「好不好看」，而是**笔画重量分布**与**题材风格是否同源**。牌面是毛笔楷书体系的东西，用宋体等于用了另一套造型语言。这条对任何「小尺寸、要一眼认出」的字符资产都成立。

## 已知未做的事

- **字形轮廓未做曲线精简**：`Sou1.svg` 那种手绘追踪曲线经过 compactness 优化，
  我们的轮廓是直接抽取的，路径点数偏多（十个字共 9.1 KB，楷体的笔锋曲线比宋体复杂
  2.7 倍）。目前影响可忽略（打包进 HTML 的只有脚本源码 ~10 KB；每个牌面字符串是运行期
  生成后即丢弃），若将来需要，可引入曲线简化作为构建步骤。
- **牌桌度量未抽成独立描述文件**（KDE 的做法）：目前几何常量写在 `tiles-ui.js`
  顶部（`BX/BY/BW/BH/PX/PY/PW/PH`），尚未进 `tokens.js`。几何与色板混在一起时
  改版式风险更高，是下一轮的候选。
- **万子版式的字号还未做成参数化推导**：`WAN_LAYOUT` 的四个数值是按「最高墨迹」手算
  出来的，改字号要靠 `tiles.smoke.mjs` 的越界断言兜住。更稳的做法是从各字形的墨迹
  包围盒自动求解版式（给定面板内区与段间距，解出最大可用字号），可留作下一轮。
- **首轮调研以牌面为主**，牌桌 UI 外壳（按钮、抽屉、对局记录）尚未对标过开源实现。
